# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TRACEWIRE is a branching-timeline tracker. For a tracked entity (person, organization, event, asset, topic), it builds a tree where statements are **branch points**, later events are **timelines**, contradicting events are **divergences**, and stories rejected by vetting are **pruned branches**, shown faded with the reason. Data comes from live web sources via Context.dev, and every source is vetted for manipulation. Everything is stored in MongoDB Atlas (with Atlas Vector Search), and a chat assistant answers questions using graph-aware retrieval. It is a hackathon project (Context.dev and Hostinger tracks) deployed on a Hostinger VPS.

## Non-negotiable principles (enforce in code)

1. **Evidence:** every node and edge stores a verbatim quote and a source URL. Run it through `verifyQuote` (`backend/src/utils/quotes.ts`, substring match after normalization) and discard the item if it fails.
2. **Never overclaim:** edge `basis` is `stated` | `sequence_only` | `inferred`. Wording like "caused by" is allowed only when basis is `stated`. Otherwise use neutral wording such as "followed" or "was later contradicted by".
3. **Abstain:** verdicts are `credible` | `uncertain` | `manipulative`. Missing signals (e.g. a failed RDAP lookup) lower coverage/confidence and never count as risky or safe.
4. **Neutral:** no intent inference. For assets, show no trading advice, include a "not financial advice" note, and never imply that a story caused a price move.
5. **Fail visibly:** sources that can't be scraped are stored with `readable=false` and `fetch_error`.

## Commands

From the repo root (see `Makefile`):
- MongoDB runs on MongoDB Atlas (cloud). Set `MONGODB_URI` in `.env` to the `mongodb+srv://` string. The Atlas user needs `readWrite` + `dbAdmin` on the database, because migrate runs `collMod`. `make up` starts backend + frontend in Docker, and `make prod` adds Caddy (HTTPS, uses `DOMAIN`).
- `make migrate`, `make dev` (tsx watch), `make test`, `make typecheck`.

In `backend/`:
- Run a single test file with `npx vitest run test/quotes.test.ts`, or a single test with `npx vitest run -t "rejects paraphrase"`.
- Tests use mocked external APIs. `vitest.config.ts` injects a dummy `MONGODB_URI`, because `config.ts` validates the env at import time.

Config is parsed with zod in `backend/src/config.ts`. See `.env.example` for the available variables.

## Architecture

- **Backend** (`backend/`): Node 20, TypeScript (ESM/NodeNext, so imports use `.js` extensions), Express 5 (with `pino-http`), `mongodb`, and `zod`.
  - `db/schema.ts` defines document types, `$jsonSchema` validators (enums, 0..1 ranges, edge `from_id != to_id`), indexes and vector search indexes for every collection. `_id`s are UUID strings (`newId()`). `node_entities` / `node_sources` are embedded in `nodes` as `entities[]` / `sources[]`.
  - `db/migrate.ts` applies `schema.ts` idempotently (create collection or `collMod`, `createIndexes`, create/update the `vector_index` search index with `numDimensions = EMBEDDING_DIM`). It runs on every container boot. `EMBEDDING_DIM` must match the embedding model; a mismatch with the existing index fails migrate, because changing models means re-embedding everything.
  - `db/client.ts` exports `col.*` typed collections, `withTransaction` (wrap each article's writes in one transaction; pass `session` to every op) and `withEntityLock` (a lease document in `locks`, renewed while held, so cron, webhook and manual refreshes never overlap).
  - `db/vectorStore.ts`: same setup as Agentic-GitPayBit. LangChain `MongoDBAtlasVectorSearch` + `OpenAIEmbeddings` (pointed at `EMBEDDING_BASE_URL` / `EMBEDDING_API_KEY` / `EMBEDDING_MODEL`, currently the MongoDB embedding API with `voyage-4`), with `indexName: "vector_index"`, `textKey: "embedding_text"` and `embeddingKey: "embedding"`. Store with `getVectorStore(collection).addDocuments(docs, { ids })`, which upserts `{_id, embedding_text, embedding, ...metadata}` and takes no session. Search with `similaritySearchWithScore(query, n)`, as the `search_nodes` tool does.
  - Writes are idempotent through upserts against unique indexes on `sources.url`, `edges(from_id,to_id,type)` and `metrics(entity_id,name,observed_at)`.
  - `clients/contextdev.ts`: Context.dev response shapes are under-documented, so all parsing goes through `normalizeSearchResults` / `normalizeScrape`. The first raw response per endpoint is dumped to `DEBUG_RAW_DIR`. A 200 response can still contain `success:false` outputs. Requests are queued under a concurrency limiter (`CONTEXT_DEV_CONCURRENCY`, API max 50) and retry on 408/429/5xx while honoring `Retry-After`. A 402 is not retried.
  - `clients/llm.ts`: an OpenAI SDK client pointed at the Hostinger AI Router. `completeJson` uses temperature 0 and JSON mode, validates the output with zod, and retries once on invalid output.
  - `clients/embeddings.ts`: the legacy `EmbeddingProvider` is either `router` or `python_service` (`POST /embed {texts} -> {vectors, model, dim}`), selected by `EMBEDDING_PROVIDER`. The vector store does not use it; it uses `OpenAIEmbeddings`. MongoDB stores and compares vectors via `$vectorSearch` (cosine) on `vector_index`.
  - `agent/`: chat agent on LangGraph.js. `graph.ts` runs a ReAct loop (`agent` node = `ChatOpenAI` via the AI Router with tools bound, `tools` node = `ToolNode`) and is built by `createAgentGraph({model, checkpointer})` so tests can inject a fake model and `MemorySaver`. `checkpointer.ts` stores thread state in Mongo (`agent_checkpoints`, `agent_checkpoint_writes`), keyed by `thread_id`. `prompts/system.ts` turns the non-negotiable principles into the system prompt: a report prompt for any public subject (politician, business leader, company, public figure, country, climate, disaster, conflict, event). `prompts/live.ts` is the live-tracking prompt (source playbooks per subject type, baseline, a `monitor-plan` JSON block in the `CreateMonitorRequestDto` shape, LIVE UPDATE cards). `buildSystemPrompt(entityId, userMessages)` switches a thread to it once `isLiveTrackingRequest` matches a user message ("track"/"follow" only count together with update words). The tools in `tools/` are stubs that return `not_implemented`, with the intended Mongo query in a TODO. `index.ts` (`runAgent`, `getThreadMessages`) is the only module routes import. `mongodb` is pinned to v6 because `@langchain/langgraph-checkpoint-mongodb` depends on v6 and shares our client.
  - `routes/chat.ts`: `POST /chat {message, thread_id?, entity_id?}` returns `{thread_id, reply, messages}`. Omit `thread_id` to start a new thread. `GET /chat/:threadId` returns the thread history.
  - Planned modules (not yet built): `ingest/` (discover → scrape → vet → extract per entity type → dedupe → link), `graph/tree.ts` (`$graphLookup` over `edges`, `maxDepth: 3` for depth 4; `$graphLookup` dedupes visited nodes, so cycles terminate), `graph/ragContext.ts`, routes, `jobs/scheduler.ts` (node-cron), and `eval/`.
  - `research/`: `/prompt` (the frontend prompt bar) returns 202 and runs `runResearch` in the background. It creates a spine node for the query (or uses `selectedNodeId` in `mode: "branch"`) and runs the agent with only `context_get-news-search` + `context_web-search` and `RESEARCH_PROMPT`, streaming its steps. Every tool result is parsed by `extractArticles`, which reads `url`/`title`/`description`/`source` from the raw tool JSON and never from LLM text. Articles are filtered by `isRelevant`, which requires every significant query word, then deduped by normalized URL (stable `art-<hash>` ids) and capped at 10 per result and 25 total. Each one is broadcast as `branch:created`. The agent's closing summary becomes the node's `info` (`node:updated`).
  - `investigations/` + `routes/investigations.ts`: TRACEWIRE investigation API, following `contracts/investigations.ts` and `docs/investigation-contract.md`. `backend/src/investigations/types.ts` mirrors the root contract (the Docker context is `backend/`), so keep them in sync. `InvestigationService` create/extend starts a background ResearchRun using `collectArticles()` (shared with the timeline's `runResearch`), appends one event per run with articles as evidence, bumps `revision` on every change, and publishes `investigation:updated` on `/ws`. Only one active run is allowed per investigation (409). Storage is `MongoInvestigationStore` (`investigations` + `research_runs`) or memory when `TIMELINE_MOCK=true`. Runs left in flight are marked failed on startup, in the background.
  - `investigations/chat.ts` (`ResearchChatService`) is graph-first: the graph is the answer and the chat is a short pointer. `answer_question` uses `graphQa.ts`, which builds a labelled listing of what is currently in the graph (claims C1.. with status, articles E1..). `GRAPH_QA_PROMPT` asks for JSON `{found, answer (2 sentences max), claims, evidence}`. `resolveAnswer` maps labels to ids, and the highlight is sent both as an SSE `highlight` event (nodeIds plus evidenceIds) to the asking client and as `/ws investigation:highlight` to every viewer. If the graph doesn't cover the question, the chat says so and suggests extending. Extend, Verify and Build claims reply with one line; Verify's full comparison lives in `ProofReportDto.summary`, shown collapsed in the proof card. `GET /investigations/:id/messages` returns history from `chat_messages`; `POST /investigations/:id/research` streams SSE.
  - `proof/` (proof engine, chat action `verify_sources` + `eventId`): `articles.ts` picks up to 8 articles under the event (one per publisher) and scrapes their full text through the Context.dev MCP `context_web-scrape` tool; unreadable pages are kept with their error. `agents.ts` holds the Corroborator (facts shared by 2 or more outlets) and the Skeptic (angles, unique details, contradictions), both run as JSON via `completeJson` in parallel. `verifyFindings` keeps only quotes that verify verbatim (`verifyQuote`) and requires 2 or more outlets per shared fact and per dispute. `assignRoles` gives each article a role: dispute, consensus, angle or unreadable. `engine.ts` streams progress, then a synthesis written from the verified findings only. The result is a `ProofReportDto` (stored on the message) and `investigation:highlight` frames with `roles`. The scraper and the JSON LLM are injectable for tests (`ResearchChatService` `proof` dep).
  - `claims/builder.ts` (chat action `build_claims`) builds the hierarchy Entity → Topic → chronological Claims → Evidence. It runs per-article candidate extraction (quotes verified immediately), then a merge across outlets (stances and neutral links with a basis), then a deterministic similarity fallback for candidates the merge left out. `decideStatus` marks a claim `established` with 2 or more independent outlets or a primary/official source (hedged wording doesn't count); otherwise it is `pending` with a reason, and contradicting evidence sets `disputed`. Claims, links and entity are stored on the investigation via `store.setClaims`. The frontend claim view shows established claims on the main line and pending ones on a dashed unverified lane (`claimView` and `UNVERIFIED_LANE_Y` in TreeCanvas). It also shows stance colours, link arcs and an Entity › Topic breadcrumb.
  - `monitors/` (live monitors, Context.dev Monitors API): `POST /investigations/:id/monitors {kind: news_feed|page|sitemap, url?, instructions?, intervalMinutes}` creates a Context.dev monitor (`news_feed` = page monitor on a Google News RSS search for the topic, exact detection; `page` + instructions = semantic). Changes arrive three ways that all meet in `MonitorService.apply` (idempotent per change id, queued per investigation): the signed webhook `POST /webhook/monitor` (HMAC `X-Context-Signature` over the raw body, registered only when `PUBLIC_BASE_URL` is public https), the poller (`MONITOR_POLL_MS`, `GET /monitors/:id/changes?since=`), and "Check now" (`POST …/check` → run → wait). `ingest.ts` turns a change into evidence from the change record only (new links in the diff, minus re-ordered ones; sitemap `added_urls`; or the page itself), adds a `Live update · …` event, rebuilds claims with that evidence preferred (`buildClaims({prefer})`), highlights new claims and narrates progress as `/ws investigation:monitor`. Monitors (incl. the signing secret) are embedded in the investigation doc and stripped from every DTO. `GET …/monitors/suggestions` (`liveSources.ts`) finds pages updating right now: news search for "<topic> live updates/live/latest", scored by live signals in URL/title and recency, then the top 3 are scraped fresh and ranked by timestamped update entries on the page (unreadable ones kept with their error). Frontend: `LiveMonitor.tsx` (LIVE toggle + panel with "Find live sources", a "Will monitor: <url>" preview and the tracked websites as links), the TRACKING strip of monitored sites and the live toast in `App.tsx`.
  - `vetting/` (source vetting = propaganda / manipulation screening, ported from `todo/propaganda-checker` + `todo/propaganda-detection`): `ratings.ts` looks up the source's domain (and parent domains) in `backend/data/source-ratings.json` (13.6k domains built by `scripts/build-source-ratings.mjs` from the labelled dataset; provenance and licences in `backend/data/SOURCE_RATINGS.md`; the Dockerfile copies `data/`). Kinds: `influence_operation` (documented covert ops: Meta CIB, VIGINUM, Citizen Lab...), `state_media`, `unreliable` (contested MBFC-style ratings), `satire`, `reliable`. `rhetoric.ts` screens page text with `completeJson`: technique quotes must pass `verifyQuote`, `likely_propaganda` needs 2+ distinct verified passages in the author's own voice, satire/non-article genres/partial text are `uncertain`. `vet.ts` `combineVetting`: manipulative = influence operation OR grounded propaganda rhetoric; credible = a positive signal and no caution listing; otherwise uncertain; missing/failed checks only lower `coverage`. `withSourceRatings(store)` attaches the domain listing to every new evidence item (free). `VettingService`: `POST /investigations/:id/vet {evidenceIds?}` (background, max 12, concurrency 3, `/ws investigation:vetting`) and `POST /vet {url}` (any website, sync). Screening is automatic (`AUTO_VET_SOURCES`, default true): `claims/pipeline.ts` `buildClaimGraph` (used by research runs, live monitors and chat build_claims) runs `vetForGraph` (screens every source `pickEvidence` would use, re-picking up to 3 rounds as pruned sources drop out) → `buildClaims` → `corroborateClaims` → `vetUrls` on the new corroborating pages (manipulative ones stored with their screening but removed from claims via `pruneClaims`, status recomputed) → store. `cachedScraper` shares page reads between screening, claim building and the proof engine. Propaganda score: `rhetoric.score` (0-100, clamped by grounding: >60 only with a verified `likely_propaganda` finding, ≤40 for `no_clear_evidence`, ≤60 otherwise) → `propagandaScore` (documented influence operations ≥90). Above `PROPAGANDA_FLAG_THRESHOLD` (60) the canvas draws a waving red flag on the source tip and on its node (count + highest score), with a hover card (score, verified technique quotes, listing). Corroborating sources pruned as manipulative stay on the claim as `prunedEvidence` (red-flagged children, never counted). Embeddings: `vetting/sourceIndex.ts` upserts every screened source into `sources` (`_id` = hash of normalized URL; `vet_verdict`, `vet_risk` = score/100, `vet_flagged`, `vet_detail`, `investigation_ids`, `embedding_text` + `embedding` via `getEmbeddings()`), fire-and-forget; `sources` has an optional `vector_index` (migrate logs instead of failing if Atlas refuses it: free tier max 3 search indexes). The agent tool `search_sources` searches it. Results live on `InvestigationEvidenceDto.vetting`; `pickEvidence` drops manipulative sources, so they never support claims (pruned: drawn faded and dashed with a tag in the canvas). Frontend: `SourceVetting.tsx` (read-only toolbar badge `SourceVettingBadge`: screened count, red-flagged count, live progress in its tooltip; `VettingCard` in the detail panel and node cards).
  - `newspaper/` (front page of an investigation, design from `todo/modern-newspaper.html`): `edition.ts` `buildEdition` picks claims deterministically (lead = newest established claim with the widest sourcing, then stories, then briefs; chronology; propaganda watch) and an editor LLM (`EDITOR_PROMPT`) only writes kicker/headline/dek/lead paragraphs from the supplied claims C1..; paragraphs must cite known labels or are dropped; unverified claims get an "Unverified" kicker; failure -> fallback composed from claim statements. Manipulative sources never appear as stories, sources or images. Images: article `imageUrl` (kept from news search `image_url` by `extractArticles`) or og:image via REST `scrape()` metadata, cached. `render.ts` renders the escaped broadsheet HTML (greyscale photos, generated art fallback, posts `tracewire:newspaper-height`). `NewspaperService` caches per `editionStateKey` (claimsUpdatedAt + evidence + flags). Routes: `GET /investigations/:id/newspaper` (JSON) and `/newspaper.html` (strict CSP). Frontend: `NewspaperEdition.tsx` renders it in a sandboxed iframe below the graph (`.gh-main-column` scrolls; "Today's edition ↓" button), reloading on run completion, live claims updates, vetting done and chat graph updates.
  - Request logs redact `cookie`, `authorization` and `set-cookie` headers.
  - `realtime/hub.ts` + `routes/timeline.ts` + `timeline/`: the backend side of the frontend contract in `frontend/README.md`. REST covers `/timeline`, nodes, branches, `/timeline/events`, `/status` and `/prompt`. `/scrape-*` returns 501 until ingest exists. Every mutation is saved by `MongoTimelineStore` (`timeline_nodes` with branches embedded, plus a version counter in `timeline_meta`) and broadcast on the `/ws` WebSocket. The hub sends `timeline:init` on connect, answers `ping` with `pong` and `timeline:sync` with a fresh `timeline:init`, and drops dead clients. `timeline/types.ts` mirrors `frontend/src/types/tree.ts`, so keep them in sync. Routes are served both at `/` and under `/api`. With `TIMELINE_MOCK=true`, the server uses an in-memory store seeded from `timeline/mock.ts`, which holds demo data built from the frontend's README and test fixtures (marked `Demo data`, `scrapeEngine: 'seed'`, no real source URLs). When the first WebSocket client connects, it replays `MOCK_LIVE_STEPS` every `TIMELINE_MOCK_INTERVAL_MS` (default 4000), so the graph grows live. MongoDB is not needed in this mode.
- **Frontend** (`frontend/`): React + Vite + Tailwind "Signal Spine" timeline. `npm run dev` serves on :5173 and proxies `/api/*` (prefix stripped) and `/ws` to `BACKEND_URL` (default `http://localhost:3000`). `npm run dev:mock` runs its standalone in-memory mock server instead.
